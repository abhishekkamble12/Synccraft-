1. ARCHITECTURE DECISIONS (write these into docs/DESIGN.md on Day 1)
-------------------------------------------------------------------------------
Conflict resolution : CRDT - RGA (Replicated Growable Array), written by you.
                      Why not OT: OT needs a central server to transform ops
                      and is fragile with long offline sessions. A CRDT merges
                      ops in any order, so offline edits and reconnects are
                      naturally safe. Trade-off: tombstones use more memory
                      (handled with snapshots + tombstone GC, Day 6/8).

Character identity  : (lamport_clock, site_id) - globally unique, totally
                      ordered. Concurrent inserts after the same character are
                      ordered by the higher ID first -> deterministic.

Idempotency         : every op has a unique op_id. Applying an op twice is a
                      no-op. This is what makes reconnect safe (no duplication).

Transport           : WebSockets via Django Channels, Redis channel layer
                      (lets you run several server processes = horizontal scale).

Persistence         : append-only operation log in PostgreSQL + periodic
                      snapshots. The log IS the edit history.

Revert              : implemented as NEW ops that turn the current state into
                      the old one. History is never rewritten, so revert is
                      itself convergent and auditable.

Presence            : separate, ephemeral channel (Redis only, never in the log).

              anchor_end (CharIds), prompt_version, input_tokens,
              output_tokens, latency_ms, created_at
Suggestion    id, document, ai_job, anchor_start, anchor_end, proposed_text,
              status (open/accepted/rejected)

-------------------------------------------------------------------------------

                   "head_seq":57}

server -> client  {"type":"ack","op_id":"...","seq":58}
client <-> server {"type":"presence","user":"A","color":"#e66",
                   "cursor_anchor":"12@site3"}
server -> client  {"type":"error","code":"forbidden|bad_op|rate_limited"}
client -> server  {"type":"ai_request","kind":"rewrite","instruction":"make
                   it formal","anchor_start":"5@s1","anchor_end":"40@s2"}
server -> group   {"type":"ai_status","job":"...","status":"running"}
server -> group   normal {"type":"op"} messages from site "ai-<job>"
                  (the AI's edits travel exactly like a human's edits)
client -> server  {"type":"ai_cancel","job":"..."}

6A. AI FEATURES (DAYS 8-9) - the "AI done right" layer
-------------------------------------------------------------------------------
THE BIG IDEA (this is your interview headline):
  "The AI is just another collaborator in the CRDT."
  The AI gets its own site_id and writes to the document by emitting
  normal insert/delete ops. So AI edits:
    - stream live to everyone, character by character
    - merge conflict-free with humans typing in the SAME paragraph
    - show up in the edit history with author = "AI"
    - can be reverted like any other edit
  Most "AI editor" projects overwrite the whole document with the model's
  answer, which destroys concurrent human edits. Yours can't, by design.
  That is a distributed-systems answer to an AI problem - exactly the
  kind of thinking big tech interviewers look for.

WHY IT IS HARD (mention these in DESIGN.md):
  - Humans keep typing while the model is generating (seconds) -> the AI
    anchors its edits to CharIds, never to integer positions.
  - If the user deletes the text the AI is rewriting -> the AI's inserts
    still converge; the job detects the anchor was deleted and cancels.
  - LLM calls are slow and can fail -> they must never block the
    WebSocket consumer (run them in Celery workers).
  - Document text is untrusted input -> prompt injection risk.
  - Cost -> per-user rate limits and token budgets.

FEATURES (in priority order):

  F1 [MUST] AI co-author: "Rewrite / fix grammar / shorten / continue"
      - user selects text, picks an action (or types an instruction)
      - consumer creates an AIJob, enqueues a Celery task, returns at once
      - task reads the current text between the two anchors, calls the
        LLM with STREAMING, and agent_peer.py converts each streamed chunk
        into CRDT insert ops (plus deletes for the old text), published
        through the Redis channel layer like any other op
      - Cancel button stops the stream; partial edits stay revertible
      - UI shows a coloured "AI is writing..." presence cursor

  F2 [MUST] "What changed while I was away?"
      - on reconnect (Day 5 sync), if many ops were missed, offer a
        summary: group ops since last_seq by author, rebuild before/after
        text, ask the LLM to summarise the diff in 3 bullets
      - ties AI directly to your offline/sync feature and history log
      - cache the summary per (document, from_seq, to_seq)

  F3 [SHOULD] Suggestion mode (like Google Docs "Suggesting")
      - AI proposes a change as a Suggestion anchored to CharIds instead
        of editing directly; others see a highlight
      - Accept -> converted into real ops; Reject -> discarded
      - anchors stay correct even while others edit around them

  F4 [SHOULD] Ask the document / semantic search (RAG)
      - on snapshot, split the text into chunks, embed them, store them in
        PostgreSQL with pgvector
      - "Ask" box: retrieve the top-k chunks, answer with citations
        that jump to the matching text in the editor
      - search across all of the user's documents by meaning

  F5 [COULD] AI edit-history explainer: "Why did this paragraph change?"
      - uses the op log + authors to explain the evolution of a section

ENGINEERING REQUIREMENTS FOR THE AI LAYER (this is what earns credit):
  [MUST]   Provider-agnostic ai/client.py (one interface, easy to swap
           models); API key only from environment variables
  [MUST]   Async: Celery + Redis broker, timeouts, retry with backoff,
           job status pushed over the WebSocket
  [MUST]   Guardrails:
             - document text wrapped as clearly-delimited data in the
               prompt; system prompt says never follow instructions in it
             - output validation (length limits, no empty rewrite)
             - AI can only edit inside its anchor range (enforced by
               agent_peer.py, not trusted to the model)
  [MUST]   Limits: per-user requests/min and daily token budget; show a
           friendly error when exceeded
  [MUST]   Graceful degradation: if the LLM is down, the editor keeps
           working 100%; AI buttons show "unavailable"
  [MUST]   Tests with a FAKE LLM client (deterministic, no network):
             - AI rewrites a paragraph while 2 humans type in it
               -> all replicas converge, no human character lost
             - cancel mid-stream -> no duplicate or orphan ops
             - LLM timeout -> job marked failed, doc unchanged
  [SHOULD] Observability: tokens, latency, cost and failure rate per
           feature as Prometheus metrics; store them on AIJob
  [SHOULD] Evals: ai/evals/ with ~30 examples (input, instruction,
           expected properties, e.g. "meaning kept", "shorter than
           input"); script scores prompt versions -> put results in
           BENCHMARKS.md. Versioned prompts in prompts.py.
  [COULD]  Caching identical requests; smaller/cheaper model for
           summaries, stronger model for rewrites (explain the trade-off)

-------------------------------------------------------------------------------

  - Explain CRDT vs OT. When would you choose OT? (Google Docs uses OT with
    a central server; CRDTs suit peer-to-peer and offline-first apps.)
  - Walk through two users typing at the same index at the same time.
  - Why Lamport clocks and not wall-clock time? (clock skew)
  - How do you guarantee exactly-once effect over at-least-once delivery?
    (idempotent apply + unique op_id)
  - What happens if the server crashes between saving and broadcasting?
  - Tombstones grow forever - how would you fix it?
  - How would you scale to 1 million documents / 10k editors on one doc?
    (shard by document id, sticky routing, snapshot compaction, fan-out

    make it faster?
  - Biggest bug you hit and how you found it (keep a log - see below).
  - Why is the AI a CRDT peer instead of replacing the text?
  - The AI takes 5 s to answer and the user edits the paragraph meanwhile
    - what happens? (CharId anchors, merge, cancel if anchor deleted)
  - How do you stop prompt injection from document content?
  - How do you control LLM cost and handle provider outages?
  - How do you know a prompt change made things better? (evals)
